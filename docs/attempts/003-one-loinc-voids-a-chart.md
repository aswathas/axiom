# Attempt 003 — One unfamiliar LOINC code erased a whole chart

**Opened.** 2026-10-15, found by running real ingested data.
**Closed.** 2026-10-15, commit "one unfamiliar LOINC must not void an entire chart".
Fixed.

**Hypothesis.** The clinical graph builds from Facts, and Facts come from a
controlled generator plus a deterministic table parser. The analyte vocabulary is
therefore known, and a bare dictionary lookup is safe.

**How we tested it.** Ran a real ingested chart containing a code the vocabulary did
not have.

**What actually happened.** A bare `ANALYTES[loinc]` lookup raised `KeyError` inside
`_build`. The exception propagated to a 404, and the patient listing fell back to zero
nodes.

The commit's summary of the blast radius:

> "a whole record silently erased by one unfamiliar code"

Every fact in that patient's record — every encounter, every observation, every
temporal edge — was gone, because one analyte was not in a dictionary. Not degraded.
Not flagged. Erased, and the failure surfaced as a 404, which is indistinguishable
from the patient not existing.

The fix keeps the node with a visible name and no interpretation:

> "Unknown analytes now keep their node with visible name only, rather than taking
> the chart with them."

### Why the hypothesis was wrong

It assumed the vocabulary would stay closed. That assumption is true for synthetic
data generated by the team's own patient model, and false for exactly one reason that
matters: prose extraction. The LLM prose extractor reads free text from documents,
which is the one place an unknown code can enter the system legitimately.

So the boundary that was assumed closed is the one boundary that is open by design.

### What this attempt is a reminder of

**A `KeyError` in a builder is not a small failure.** The instinct that makes
`ANALYTES[loinc]` look safe is that a missing mapping should be a small problem. In a
builder it is not: the raise happens once, in the wrong place, and everything
constructed before it is discarded with it.

The general form: **builders should degrade per-node, not fail per-document.** One
malformed record in a batch of ten thousand is a routine condition in any system that
ingests what other systems wrote. If one bad record erases the batch, the design is
wrong regardless of how good the parser is.

### The related defect, same commit

> "Also replaces an em-dash in a user-facing refusal string; it rendered as mojibake
> in a demo screenshot when a hop decoded UTF-8 as cp1252."

Two unrelated bugs in one commit, which is itself the lesson: both were found by
looking at the same screenshot. Encoding errors surface in exactly one place — where
bytes become characters a human reads — and a refusal string is a human-facing string
in a system where refusals are the important output.

**What would change this decision.** Nothing. The fix is strictly better.

### What is still open

The same failure shape exists in the entity-resolution margin, which the README
itself flags as limitation 6: the highest-scoring non-match sits 0.015 below the merge
threshold. A merge error at that margin does not erase a chart, but it merges two
patients, which in this domain is not a recoverable error and is not currently
tested.
